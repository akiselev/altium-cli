The original file stored lossy single-character approximations (`?` for OHM, `v` for SQUARE ROOT) while the roundtrip stores HTML numeric character references (`&#8486;`, `&#8730;`). Although the `%UTF8%` prefixed authoritative version is preserved correctly, the Windows-1252 fallback text is different. This is arguably an improvement in data fidelity, but it is still a value change.

## Impact on File Format Support

**What's working well:**
- All 648 pin records (RECORD=2) preserve all values including PinPropagationDelay, FormalType, Electrical, PinConglomerate, etc.
- Complex component records (RECORD=1) with database library references are fully preserved
- Wire records (RECORD=27) with multi-point coordinates serialize correctly
- The `%UTF8%` encoding of Unicode text is preserved exactly

**What needs improvement:**
- Parameter serialization order does not match Altium's native order for RECORD=2, RECORD=17, RECORD=27.
- The Windows-1252 fallback encoding for non-ASCII characters uses HTML numeric character references instead of matching the original lossy encoding. When a character cannot be represented in Windows-1252 (e.g., U+2126 OHM SIGN), Altium stores a lossy fallback (e.g., `?`). Our serializer appears to produce `&#8486;` instead. This should be investigated to determine whether Altium accepts HTML entities in Windows-1252 text fields.
- `Weight=0` is injected as a default value in the /Additional HEADER when the original omitted it. The serializer should omit default values to match original behavior.
- /Storage binary block is re-encoded with a different size.

**Specific bugs revealed:**
- **Unicode fallback encoding bug**: When a string has both `%UTF8%Key=...` and `Key=...` versions, the Windows-1252 version should preserve the original lossy encoding rather than attempting to re-encode from Unicode using HTML entities.
