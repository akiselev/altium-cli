# Altium ECO (Engineering Change Order) System

Research from decompiled AD26 .NET source code.

## Overview

Altium's ECO system synchronizes design changes between schematic and PCB documents
(and other document types like harness, multi-board assembly, etc.). The system is
built around a **comparison + change generation + change execution** pipeline:

1. Two projects are compared (source vs target, e.g. schematic vs PCB)
2. Differences produce `IModification` objects stored in a `ChangeManager`
3. The user reviews changes in a dialog (`IWSM_ChangeManagementDialog`)
4. Enabled changes are executed via `IECO` interface calls to target documents
5. Each change goes through 3 phases: CheckSupport -> Validate -> Perform

ECO changes are **not persisted to files**. They are transient in-memory objects
generated by comparison, reviewed by the user, and then applied (or discarded).
The only file output is an optional `.ECO` report generated via
`Templates\ECOReport.rtm` template.

## IECO Interface

COM interface (`{0BD898CE-E862-4DDC-85AF-BC8654AED259}`) that target documents/projects
implement to receive ECO changes. Defined in `RT_Workspace`.

```csharp
public interface IECO
{
    // Transaction boundaries
    void DM_Begin();
    void DM_End();

    // Add a new object (component, net, class, rule, etc.)
    bool DM_AddObject(TECO_Mode argMode, IDMObject argReferenceObject);

    // Remove an existing object
    bool DM_RemoveObject(TECO_Mode argMode, IDMObject argObjectToRemove);

    // Add a member to a parent object (e.g., component to class, net to class)
    bool DM_AddMemberToObject(
        TECO_Mode argMode,
        IDMObject argReferenceMember,
        IDMObject argReferenceParent,
        IDMObject argTargetParent);

    // Remove a member from a parent object
    bool DM_RemoveMemberFromObject(
        TECO_Mode argMode,
        IDMObject argMemberObject,
        IDMObject argParentObject);

    // Change a property of an existing object
    bool DM_ChangeObject(
        TECO_Mode argMode,
        TModificationKind argKind,
        IDMObject argObjectToChange,
        IDMObject argReferenceObject,
        IUpdateParameterOptions argUpdateParameterOptions);
}
```

### TECO_Mode (3 phases)

Every ECO operation is called three times, once per mode:

```csharp
public enum TECO_Mode
{
    eECO_PerformAction,         // 0 - Actually execute the change
    eECO_ValidateAction,        // 1 - Check if the change is valid
    eECO_CheckSupportForAction  // 2 - Check if the handler supports this change type
}
```

Execution order in `ChangeManager.PerformActions()`:
1. `eECO_CheckSupportForAction` -- skip if not supported
2. `eECO_ValidateAction` -- sets status to PassedVerification or FailedVerification
3. `eECO_PerformAction` -- sets status to PassedExecution or FailedExecution

### TModificationStatus

```csharp
public enum TModificationStatus
{
    eStatusNone,                // 0
    eStatusIsSupported,         // 1
    eStatusIsNotSupported,      // 2
    eStatusPassedVerification,  // 3
    eStatusFailedVerification,  // 4
    eStatusPassedExecution,     // 5
    eStatusFailedExecution      // 6
}
```

### TModificationLevel (per-project enable/disable)

```csharp
public enum TModificationLevel : byte
{
    eModificationLevel_Off,  // 0
    eModificationLevel_On    // 1
}
```

Each project can enable/disable individual modification kinds. The `ChangeManager`
checks `project.GetModificationLevel(kind)` before adding a modification.

## CustomECOImplementation (Base Handler Pattern)

`CustomECOImplementation` is the base class that implements `IECO`. It wraps each
`DM_*` method with error handling and delegates to `virtual` `ECO_*` methods that
subclasses override.

```
IECO (COM interface)
  |
  +-- CustomECOImplementation (base class - default: return false)
        |
        +-- ProjectECO (handles variant parameter changes)
```

### CustomECOImplementation pattern:

```csharp
internal class CustomECOImplementation : IECO
{
    // DM_* methods catch exceptions, log to messages panel, delegate to ECO_*
    public bool DM_AddObject(mode, refObj) {
        try { return ECO_AddObject(mode, refObj); }
        catch (Exception ex) { Message_Error("Add object", ex.Message); return false; }
    }

    // Virtual methods for subclasses to override (default: return false)
    protected virtual bool ECO_AddObject(TECO_Mode mode, IDMObject referenceObject) => false;
    protected virtual bool ECO_RemoveObject(TECO_Mode mode, IDMObject objectToRemove) => false;
    protected virtual bool ECO_ChangeObject(...) => false;
    protected virtual bool ECO_AddMemberToObject(...) => false;
    protected virtual bool ECO_RemoveMemberFromObject(...) => false;
    protected virtual void ECO_Begin() { }
    protected virtual void ECO_End() { }
}
```

### ProjectECO (Variant Manager ECO handler):

`ProjectECO` extends `CustomECOImplementation` and handles changes to project-level
variant data. It only handles 3 modification kinds:

- `eModification_ChangeParameterName` -- rename variant parameter
- `eModification_ChangeParameterValue` -- change variant parameter value
- `eModification_FullPartUpdate` -- full part replacement in variant

It also handles `ECO_AddMemberToObject` / `ECO_RemoveMemberFromObject` for
`IParameterVariation` members within `IComponentVariation` parents.

Uses `suspendProjectUpdateNotification` counter for batching (`ECO_Begin`/`ECO_End`).

## ChangeManager (Change Generation and Execution)

`ChangeManager` implements `IChangeManager` / `IChangeManager2`. It:

1. Accepts two projects (`project1` = source, `project2` = target)
2. Accumulates `IModification` objects via `CreateECO_*` factory methods
3. Stores them in a `ModificationList` (indexed by `TModificationKind`)
4. Executes them in a defined order via `ModificationOrder` array

### Execution Pipeline

```
PerformActions():
  1. Collect all target documents
  2. Get IECO interfaces for both projects
  3. Call IECO.DM_Begin() on both projects
  4. Call doc.ECO_Begin() on all target documents
  5. For each TModificationKind in ModificationOrder[]:
       For each modification of that kind:
         a. CheckSupport -> Validate -> Perform (3-phase)
         b. Set status accordingly
  6. Call doc.ECO_End() on all target documents
  7. Call IECO.DM_End() on both projects
  8. Re-compile affected schematic documents
```

### Modification Filtering

Before adding a modification, `ChangeManager` checks:
```csharp
bool IsModificationValidForProject() {
    IProject ownerProject = ChangeManagerUtils.GetOwnerProject(aModification);
    return ownerProject?.GetModificationLevel(kind) == eModificationLevel_On;
}
```

This allows users to disable specific ECO change types in project options.

## Change Flow Architecture

```
  [Schematic]          [Comparison Engine]           [PCB / Target]
      |                       |                           |
      |  compiled design      |                           |
      |  (IDocument tree)     |                           |
      +-----> IProject ------>|                           |
                              |                           |
                              | CreateECO_*() calls       |
                              | produce Modification      |
                              | objects                   |
                              |                           |
                              v                           |
                     [ChangeManager]                      |
                     ModificationList                     |
                              |                           |
                              | user reviews in           |
                              | ChangeManagementDialog    |
                              |                           |
                              | PerformActions()          |
                              |                           |
                              +--- IECO.DM_Begin() ------>|
                              |                           |
                              +--- doc.ECO_Begin() ------>|
                              |                           |
                              | for each modification:    |
                              +--- ECO_Action(Check) ---->|
                              +--- ECO_Action(Validate) ->|
                              +--- ECO_Action(Perform) -->|
                              |                           |
                              +--- doc.ECO_End() -------->|
                              |                           |
                              +--- IECO.DM_End() -------->|
```

### Dispatch at Document Level

When a `Modification` executes, it calls methods on `IDocument` (e.g.,
`doc.ECO_ChangeObject()`), which dispatches to the document's editor server
via `IDMObjectHelperExt`:

- `Document_ECO_ChangeObject` -- dispatches to schematic or PCB editor
- `Project_ECO_ChangeObject` -- dispatches to project-level handler (ProjectECO)
- `Document_ECO_Begin` / `Document_ECO_End` -- transaction boundaries per document

The PCB editor's ECO handler is in the Delphi layer (accessed via COM interop).
The schematic editor's ECO handler is also Delphi-based.

---

## Serialization / Persistence

ECO changes are **NOT serialized to Altium design files**. Key observations:

1. **In-memory only**: `Modification` objects are created, reviewed, executed, and
   discarded. There is no save/load mechanism for pending ECOs.

2. **ECO Report**: The only file output is a report generated via
   `ChangeManager.ReportChanges()`, which writes a pipe-delimited data file with
   fields: `Project|Document|DocumentKind|ModificationType|Verb|AffectedObject|
   Direction|AffectedDocument|Details|Status|CountForKind`. This is rendered using
   the `Templates\ECOReport.rtm` report template and saved with a `.ECO` extension.

3. **PCB ECO Options** (`IPCB_ECOOptions`): The PCB document stores two properties:
   - `ECOIsActive` (bool) -- whether the PCB is currently accepting ECO changes
   - `ECOFileName` (string) -- path to an ECO file (appears to be for legacy
     ECO file import, not for persisting the change list)
   These are serialized as parameters within the PCB document options.

4. **Annotation file**: `IDMObjectHelperExt.DoPushECOToAnnotationFile()` suggests
   that annotation-related ECOs (designator changes) can be persisted to an
   annotation file (`*.Annotation` in the project), but this is for back-annotation
   tracking, not general ECO persistence.

5. **WAS-IS Records**: Back-annotation uses WAS-IS record files (loaded via
   `eFilter_ECOFiles` file dialog filter) for designator rename history. These
   are simple text files with old -> new designator mappings.

## ECOCopies (Comparison Snapshots)

The `Altium.Sch.Compilation.Adapters.ECOCopies` namespace contains adapter classes
that create **snapshot copies** of design objects for ECO comparison. These are used
when pin mappings change (e.g., due to PCBLIB pin designator maps):

- `DocumentLogicalAdapterECOCopy`
- `DocumentPhysicalAdapterECOCopy`
- `DocumentFlattenedAdapterECOCopy`
- `ComponentAdapterECOCopy`
- `NetAdapterECOCopy` / `SubNetAdapterECOCopy` / `HarnessNetAdapterECOCopy`
- `NetItemPinAdapterECOCopy`

These wrap the original adapters but override pin lists to reflect mapped designators,
allowing the comparison engine to detect pin-level changes that require ECOs.
